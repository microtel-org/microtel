OpenTelemetry for C++, without the passengers.

microtel speaks OTLP, over HTTP and gRPC, without linking gRPC, Abseil or libprotobuf. Same collectors, same backends, a fraction of the dependencies.

You wanted traces. You got a dependency tree.

If you export over OTLP/gRPC with the official C++ SDK, gRPC comes with it, and with gRPC come Abseil, protobuf, c-ares and re2. You didn't choose any of them, but you build, ship, patch and audit all of them.

On servers that's friction. On edge boxes and embedded Linux it's often the reason telemetry doesn't ship at all.

microtel keeps the protocol and drops the passengers:

  • OTLP/HTTP and OTLP/gRPC over one HTTP/2 transport (nghttp2).
  • No gRPC, Abseil or protobuf-cpp. A CI check fails any change that would bring them back.
  • Works with what you already run. Any OTLP collector or backend.
  • Traces and logs supported. Metrics are available and experimental until v1.3.

gRPC on the wire is small. So we only built the wire.

01

One transport, two protocols

gRPC framing is a 5-byte prefix per message, HTTP/2 headers, and a status in the trailers. microtel implements exactly that on nghttp2, so OTLP/gRPC and OTLP/HTTP share one connection layer.

02

A small, private encoder

Protobuf encoding uses upb, from Google's protobuf project, vendored with its symbols renamed. It can't clash with whatever protobuf your application already links.

03

Kept honest by CI

Every pull request is scanned for gRPC, Abseil and protobuf-cpp symbols, and must pass ASan, TSan, UBSan and coverage floors. Conformance tests run against the real OpenTelemetry Collector on both protocols.

Measured, published, reproducible.

Ryzen 5 5600G, one host, each SDK exporting to a local blackhole sink over a container network. Measured on v1.2.6; the span timings are from v1.2.5, whose span hot path v1.2.6 leaves unchanged. Tiny device, standard OTLP.

Experimental · traces only

A C11 "leaf" builds spans in memory your firmware provides and encodes them as standard OTLP. Your code moves the bytes over whatever link the device already has: UART, CAN, BLE, UDP, MQTT. On a gateway, microtel's LeafReceiver ingests them, adds a per-device resource, corrects clocks, and exports one OTLP stream to your collector.

A minimal main.cpp that sends one span to a local collector

#include <microtel/provider.hpp>
#include <microtel/sdk_builder.hpp>
#include <microtel/span.hpp>
#include <microtel/tracer.hpp>

#include <chrono>
#include <cstddef>
#include <cstdint>
#include <iostream>
#include <string>

int main()
{
    // Build() returns microtel::Expected<std::shared_ptr<Provider>, ConfigError>.
    auto built = microtel::SdkBuilder{}
                     .WithEndpoint("http://localhost:4317")  // OTLP/gRPC, plaintext h2c
                     .WithProtocol(microtel::Protocol::Grpc)
                     .WithServiceName("checkout")
                     .WithServiceVersion("1.4.2")
                     .Build();
    if (!built)
    {
        std::cerr << "microtel: " << built.error().message << '\n';
        return 1;
    }
    const auto provider = *built;
    const auto tracer = provider->GetTracer("checkout.http", "1.4.2");

    {
        const auto span = tracer->StartSpan("GET /cart");
        span->SetAttribute("http.request.method", std::string{"GET"});
        span->SetAttribute("http.response.status_code", std::int64_t{200});
        span->SetStatus(microtel::StatusCode::Ok);
    }  // The span ends here and the batch processor exports it in the background.

    const microtel::Status flushed = provider->ForceFlush(std::chrono::seconds{5});
    // Completed means the queue drained; a batch the collector rejected also drains,
    // and a span it rejected via OTLP partial success is counted as a drop, not a failure.
    const microtel::HealthSnapshot health = provider->GetExporterHealth();
    const auto rejected = static_cast<std::size_t>(microtel::DropReason::PartialSuccessRejection);
    const bool delivered = flushed == microtel::Status::Completed && health.batches_failed == 0 &&
                           health.drop_counters[rejected] == 0;
    const microtel::Status shut = provider->Shutdown(std::chrono::seconds{5});
    return (delivered && shut == microtel::Status::Completed) ? 0 : 2;
}

Endpoints

  • grpc://collector:4317OTLP/gRPC
  • https://collector:4318OTLP/HTTP over TLS
  • http://collector:4318plaintext OTLP/HTTP. Tries h2c first and falls back to HTTP/1.1, which the stock Collector serves (since v1.2.6). HTTP/1.1 sends one request at a time; for throughput use gRPC or TLS.

Spec first. CI enforces the spec.

microtel is developed spec-first: design decisions are written down as numbered change proposals before code, and CI rejects changes that break them. Most of the code was written with Claude Code as the main coding tool, under that discipline. Testing against the real OpenTelemetry Collector caught bugs unit tests had missed; they're fixed and the tests stay.

FAQ

Is microtel a replacement for opentelemetry-cpp?

It's an alternative for C++ applications that want OTLP export without gRPC and protobuf-cpp, especially on edge and embedded targets. An experimental shim lets existing opentelemetry-cpp API code build against it.

Does it work with my backend?

If it accepts OTLP over gRPC, or over HTTP with TLS, yes. For plaintext OTLP/HTTP, see the endpoint note in Get started.

Is it production-ready?

Traces and logs are supported and conformance-tested against the OpenTelemetry Collector. Metrics, the C leaf and the shim are experimental.

Why are your numbers different from other benchmarks?

Ours measures span cost and deployed size on one machine. End-to-end overhead at a given request rate is a different question; the method is published so you can check or rerun it.
